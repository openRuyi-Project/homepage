# 导师选题发布指南

开发者只需要在 GitHub Issue 中填写项目资料，无需登录 OSPP 系统。Issue 提交后，会有专人审核并将资料录入 OSPP 发布任务。

本指南不替代 OSPP 官方规则。参与前，请完整阅读 OSPP 官方的[导师指南](https://blog2026.summer-ospp.ac.cn/help/mentor%20guide)。

## 经典模式与领航模式

| 对比项       | 经典模式                       | 领航模式                                     |
| ------------ | ------------------------------ | -------------------------------------------- |
| 项目如何产生 | 社区或导师预先确定具体任务     | 社区先提出需求方向，由学生定义问题并设计方案 |
| 学生参与方式 | 学生选择已发布的项目并提交申请 | 学生围绕需求方向提交提案并参加 Pitch         |
| 项目细化时间 | 发布前已基本确定               | Pitch 通过后，由学生和导师共同细化           |
| 项目难度     | 基础、进阶                     | 基础、进阶、挑战                             |
| 支持架构     | RISC-V64                       | x86_64、AArch64、RISC-V64 或其他架构         |

openRuyi 选题默认采用经典模式。如需采用领航模式，请先在社区内讨论，再根据讨论结果提交 Issue；请勿直接选择“领航模式项目”。

## 一、进入提交页面

1. 打开 [openRuyi OSPP Issues](https://github.com/openRuyi-Project/ospp/issues)。
2. 点击右上角的 **New issue**。
3. 根据项目报名语言选择模板:

- 只接受中文报名: 选择 **开源之夏 2026 项目提交 (仅中文)**。
- 接受中英双语报名: 选择 **开源之夏 2026 项目提交 (中英双语 / English)**。
- 只接受英文报名: 仍选择 **中英双语 / English** 模板，然后将报名语言改为 **English only**。

不要选择 **Blank issue**，否则工作人员可能无法完整收集项目资料。

## 二、语言填写规则

### 1. 仅中文项目

使用 **仅中文** 模板，所有项目资料使用中文填写。

### 2. 中英双语项目

选择 **Chinese and English**，中文和英文内容必须全部填写，不能只填写其中一种。

Issue 标题建议使用:

```text
中文项目名称 / English Project Name
```

### 3. 仅英文项目

选择 **English only**，所有英文区域正常填写；要求填写中文内容的字段统一填写:

```text
N/A
```

## 三、逐项填写项目资料

### 1. Issue 标题

将页面顶部预填的标题改成实际项目名称。

中文项目直接使用中文名称；双语项目建议使用“中文名 / 英文名”。

名称应直接体现项目采用的技术和目标任务，不要使用“项目开发”“系统优化”这类笼统名称，也不要用逗号拼接多个句子。

推荐格式:

```text
基于 <技术或技术栈> 实现 <目标>
面向 <平台或场景> 开发 <功能>
利用 <工具或软件> 完成 <任务>
```

### 2. 项目类型

经典模式项目选择:

```text
经典模式项目 / Classic Track
```

如经社区讨论确认采用领航模式，则选择:

```text
领航模式项目 / Pioneer Program
```

经典模式的支持架构在 OSPP 中固定为 `RISC-V64`。

### 3. 项目名称

填写正式项目名称。双语模板需要分别填写中文名称和英文名称，并与 Issue 标题保持一致。

示例:

```text
中文: 面向 RISC-V64 的软件包自动化构建与测试工具
英文: Automated Package Build and Testing Tool for RISC-V64
```

### 4. 项目导师

按照模板逐项填写:

```text
导师姓名:
导师邮箱:
导师贡献的 openRuyi 仓库地址:
```

注意:

- 邮箱应填写导师在 openRuyi 组织内参与贡献时使用的邮箱。
- 仓库地址应能体现导师对 openRuyi 项目的实际贡献。

导师注册说明:

- 一位导师最多指导两个项目；填写多位导师时，也需要逐一确认每位导师的项目数量。
- 首次参加 OSPP 的导师在组织联系人录入导师信息后会收到邀请邮件，通过邮件中的链接登录系统完成身份验证。**所属组织名称** 填写 `openRuyi`，**贡献仓库** 填写本人实际贡献的 openRuyi 仓库地址。
- 此前已注册过 OSPP 导师的，使用原账号登录并完成身份验证，同时检查 **所属组织名称** 和 **贡献仓库**: 所属组织应为 `openRuyi`，贡献仓库应为本人实际贡献的 openRuyi 仓库地址；如有不符，需及时修改。
- 导师不得同时以学生身份参加本届活动。

### 5. 项目描述

项目描述需要同时包含以下五项信息:

```markdown
## 相关背景

说明项目所在领域、使用场景及为什么需要开展该项目。

## 已有工作

说明当前仓库、软件或社区已经具备哪些能力。

## 存在的不足

说明目前缺失的功能、性能问题或使用限制。

## 希望改进的点

说明准备解决哪些具体问题。

## 最终项目实现的目标

说明项目完成后应具备哪些能力以及如何判断完成。
```

这五项不要写成五个单独的小节，应组织成一段逻辑连续的项目说明。英文项目应编写对应的英文段落，不要只把中文标题翻译成英文。

### 6. 项目备注

GitHub Issue 模板中该项为必填:

- 没有补充事项时，中文填写 `无`，英文填写 `None`。
- 为便于录入 OSPP，中文内容不要超过 5000 字，英文内容不要超过 10000 字符。

### 7. 项目综合难度

经典模式只能选择:

- **基础 / Basic**
- **进阶 / Advanced**

**挑战 / Challenge** 仅适用于经社区讨论确认的领航模式项目。

### 8. 开发周期

根据预计工作量选择:

- **2 个月**
- **3 个月**
- **4 个月**

### 9. 技术领域标签

可选择一个或多个领域:

- **开源芯片**
- **应用软件开发**
- **大数据与人工智能**
- **开发和运维**
- **分布式系统**
- **操作系统与基础软件**
- **网络与安全**
- **编程语言**

选择与项目核心工作直接相关的领域，不要为了扩大曝光而全部选择。

### 10. 编程语言标签

填写项目实际使用的编程语言，多个语言使用英文逗号分隔:

```text
C, C++, Rust
```

不要在这里填写框架、操作系统或数据库名称。

### 11. 项目产出要求

使用编号逐条填写学生需要完成的工作和预期效果:

```text
1. 完成 RISC-V64 自动化构建模块。
2. 为核心组件恢复上游测试。
3. 输出功能测试和性能测试报告。
4. 编写安装、使用和维护文档。
```

要求:

- 每项只描述一个可检查的成果。
- 中文每项建议控制在 30 字以内。
- 避免“熟悉项目”“学习相关知识”等无法验收的描述。

### 12. 项目技术要求

从编程语言、技术栈和开发经验三个方面填写:

```text
1. 熟悉 C/C++，能够阅读现有工程代码。
2. 熟悉 Linux 开发环境及 Git 工作流。
3. 了解 RISC-V 架构和交叉编译。
4. 有 QEMU 或 Buildroot 经验者优先。
```

建议使用“掌握”“熟悉”“了解”“有相关经验者优先”等明确表述。中文每项建议控制在 30 字以内。

### 13. 项目成果仓库

填写组织已经存在、用于接收项目成果和 PR 的仓库根地址:

```text
https://github.com/openRuyi-Project/<repository-name>
```

要求:

- 必须是已有仓库，不能是新建空仓。
- 必须填写完整的 HTTPS 仓库根地址。
- 不要填写组织主页、分支、目录、Issue 或 SSH 地址。
- 不要附加说明文字或 `.git`。
- 多个仓库使用英文逗号分隔。

### 14. 仓库开源协议

填写成果仓库实际使用的 SPDX 协议标识，例如:

```text
Apache-2.0
MIT
GPL-2.0-only
```

如有多个仓库，请按照仓库链接的顺序依次填写对应的协议标识，并使用英文逗号分隔。协议标识须与仓库一一对应，相同协议也需重复填写。

## 四、提交前检查

提交前确认:

- 项目类型选择正确；如采用领航模式，需提前在社区讨论。
- 名称能体现技术和目标。
- 导师姓名、邮箱和贡献仓库完整。
- 项目描述的五个部分均已填写。
- 产出要求能够逐项验收。
- 技术要求与项目难度匹配。
- 成果仓库是有效的仓库根地址。
- 开源协议填写正确。
- 双语项目的中英文内容一一对应。

确认无误后，勾选:

```text
我确认所填信息完整准确，并已按所选报名语言填写对应内容。
```

然后点击 **Create** 提交 Issue。

## 五、提交后的处理流程

1. 开发者提交 GitHub Issue。
2. 工作人员检查资料是否完整。
3. 如有问题，工作人员会在 Issue 评论中提出修改要求。
4. 开发者直接编辑原 Issue 补充资料，不要重复创建新 Issue。
5. 信息确认完成后，由专人录入 OSPP 发布任务。
6. 在工作人员确认录入完成前，请不要自行关闭 Issue。
